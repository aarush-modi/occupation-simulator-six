# Plan: Workshift oil rig vertical slice

## Task Description
Build the first fully playable Workshift scenario: "Oil rig worker".
The player opens the lobby, sees the occupation prompt already filled in with "Oil rig worker", and presses Play.
They spawn in first person on the drill floor of an offshore platform at golden hour and work a short shift (about 6 real minutes, framed as a 12-hour tour).
The shift has a briefing, routine work with skill checks, a mid-shift well-control emergency that changes the task, a judgment call, and an end-of-shift review.
Up to four players can share the shift through a QR or link invite, with a Node room server that owns task state, holds, handoffs, and events.
Every 3D asset (props, stations, the platform, the ocean, the sky, the characters, the first-person hands) is generated by our own code from data recipes.
No downloaded models, textures, or HDRIs.
The visual target is a GTA 6-like cinematic look: warm golden-hour light, worn physical materials, ambient occlusion, bloom, filmic tone mapping, and a color grade.
Sound is synthesized with WebAudio, also our own.

The repo today is a scaffold: `frontend/` (Next.js 16, one static page), `backend/` (Node HTTP server with `GET /health`), and `REQUIREMENTS.md`.

## Objective
When this plan is complete, running the backend and frontend locally lets a player open `http://localhost:3000`, press Play on the prefilled "Oil rig worker" prompt, and finish a complete oil rig shift in first person with keyboard and mouse (and optionally webcam).
The shift is assembled at runtime from a validated scenario blueprint that references only IDs in our procedural asset catalog.
Two to four browsers can join the same room by QR or link, see each other's avatars, hand off a held prop, and experience the same mid-shift event.
The scene renders with our own procedural assets and the cinematic post-processing stack.

## Assumptions
- **One scenario, prefilled prompt.** The lobby input is prefilled with "Oil rig worker" and the Play button starts it. Arbitrary occupations, spoken prompts, and generation edge cases are out of scope (the user said the only player is them). Flag if you want free-form prompts in this slice.
- **The blueprint is a hand-authored fixture.** `shared/scenarios/oil-rig.json` is written in exactly the shape Gemini will later produce. A `POST /api/rooms` call with a `GEMINI_API_KEY` set may call Gemini with the catalog and fall back to the fixture on any failure. No acceptance criterion depends on Gemini.
- **Procedural assets only** (user decision). Every mesh is built from our recipe engine. drei's `<Sky>` (a shader, no download) and `<Environment>` with `<Lightformer>` children (procedural, no HDRI) are allowed. `drei <Text>` must use a font file committed to the repo, not the CDN default. Fonts are the only binary assets, and we pick an OFL-licensed font committed under `frontend/public/fonts/`.
- **About 60 props for this slice**, not 200. The engine and catalog are built to scale to 200+ later. Flag if you want 200 now.
- **Physics split (deviation from N3).** The server is authoritative for players, holds, prop ownership and placement, objectives, NPC goals, and events, at 20 snapshots per second. Rapier runs client-side only, for the local player's character controller against static colliders. Props never free-fall. They are either resting in a zone, held by a player, or carried. This keeps the server simple and deterministic. Flag if you want full server-side rigid-body physics.
- **Keyboard and mouse is the primary control scheme.** Webcam control (MediaPipe) is a toggle that maps to the same intents. Requirements F3 and F8 are satisfied in webcam mode, but the slice must be fully completable with keyboard and mouse.
- **Solo play goes through the backend.** A solo game is a room of one. There is one code path for game logic.
- **TypeScript** for new code in `frontend/`, `backend/`, and a new `shared/` workspace. The scaffold's two JS files are converted.
- **Career facts in the review screen** are qualitative (rotation schedule, job ladder, typical hazards) unless a number is sourced. No invented wage figures.

## Problem Statement
Workshift's pitch is "type a job, live a shift of it".
Nothing playable exists yet, and the team has not proven the hardest parts end to end: a believable 3D workplace made from our own procedural assets, a fun first-person loop built from a few reusable verbs and skill checks, a task that changes mid-shift, and shared state across several players.
One polished scenario proves all of it and becomes the template every other occupation reuses.

## Solution Approach
Data drives everything, so the oil rig is the first instance of a general system.

1. **Shared contracts** (`shared/`): Zod schemas for the prop recipe, the catalog, the scenario blueprint, and the network protocol. A pure, deterministic game-logic reducer (`applyIntent`, `tick`) that the backend runs and tests exercise.
2. **Procedural asset engine** (`frontend/src/assets/`): a recipe is JSON listing parts. Each part is a primitive (box, roundedBox, cylinder, sphere, capsule, cone, torus), a lathe profile, an extruded 2D shape with bevel, a tube along a path, a repeat/array of another part (grating, ladders, lattice), or a CSG subtraction. Each part has a material ID from a shared material library, an optional `collider` flag, and an optional name used for interaction zones and grip points. The engine merges static parts per material for draw-call efficiency and emits Rapier collider specs.
3. **Material library** (`frontend/src/assets/materials.ts`): `MeshPhysicalMaterial` presets (safety-yellow painted steel, rig-red painted steel, galvanized grating, rusted steel, chrome, rubber, hi-vis fabric, coverall fabric, glass, dark plastic, concrete, emissive screen, emissive warning light). A grime shader injected with `onBeforeCompile` adds world-space noise dirt, height-based grime at floor level, vertical rust streaks, and edge wear, so nothing looks clean. Each preset has `customProgramCacheKey`.
4. **Look-dev** (`frontend/src/look/`): low golden-hour sun with 2048 shadow map following the player, drei `<Sky>`, procedural `<Environment>` with Lightformers for reflections, a custom Gerstner-wave ocean shader with fresnel and sun glint (no texture), distance fog, then `EffectComposer` with N8AO, Bloom (flare stack, floodlights, screens, alarm strobes), HueSaturation, BrightnessContrast, Noise, Vignette, and AgX ToneMapping last, with the renderer's own tone mapping disabled. A `quality` setting (`high` default, `lite` via `?quality=lite`) turns off AO and bloom and lowers shadow resolution for tests and weak GPUs.
5. **Characters** (`frontend/src/characters/`): procedural humanoids from the same recipe engine (capsule limbs, coveralls, hi-vis vest, hard hat, boots, gloves), with procedural animation (walk cycle, idle breathing, point, talk gesture, look-at). Faceless stylized heads by design. The local player sees procedural gloved first-person hands. Remote players render as full avatars with a name tag.
6. **Gameplay client** (`frontend/src/game/`): Rapier character controller with pointer-lock mouse look and WASD. Center-screen raycast picks the nearest interactable within 2.5 m. The HUD shows a contextual prompt ("E  Pick up drill pipe"). Held props attach to a hand anchor in view. Placement shows a ghost in the target zone. Three skill-check widgets: **timing** (stop a moving needle in a band), **steady-hold** (keep a drifting needle in a band for N seconds using A/D or the mouse wheel), **press-hold** (hold a key for N seconds without releasing). The client sends intents and renders server snapshots, interpolating remote players and NPCs.
7. **Room server** (`backend/`): HTTP `POST /api/rooms` (create room, returns `roomId` and invite URL using the host's LAN IP), `GET /api/rooms/:id`, `GET /health`; WebSocket `/room/:id`. Each room holds up to four players, runs the shared reducer, ticks at 20 Hz, runs the event director and NPC goal machines, and broadcasts snapshots. Simultaneous grabs resolve to one holder. Disconnects release held props after a 3 s grace period.
8. **Lobby and flow** (`frontend/app/`): `/` is the lobby with the prefilled prompt, Play, and Invite (QR code plus copy link). `/play?room=ID` is the game. The review screen ends the shift.
9. **Audio** (`frontend/src/audio/`): WebAudio-synthesized wind, ocean, diesel engine hum, drawworks whine, footsteps on grating, UI ticks, and the kick alarm. No sample files.

### The oil rig shift (content contract)

Setting: offshore platform drill floor at golden hour, open ocean to the horizon.
Shell: steel deck about 30 m by 24 m with grating sections, perimeter railings, the derrick tower over the rotary table, a V-door ramp to the pipe deck, a pipe rack, the doghouse (driller's cabin) with windows and screens, two mud pumps, a choke manifold, the BOP (blowout preventer) control panel, a crane pedestal and boom, shipping containers, a flare stack boom with a live flame, floodlight masts, and a helideck visible across a gap.

Roles: the player is a floorhand.
NPCs: Toolpusher "Rhodes" (white hard hat, the boss), Driller "Okafor" (in the doghouse at the console), Derrickhand "Mia" (on the monkeyboard up the derrick, idle animations), Floorhand "Dez" (patrols between pipe rack and rotary table, can help).

Objectives, in order:
1. **Report in.** Walk to Rhodes at the doghouse and press E. Briefing subtitles play.
2. **Suit up.** Take a hard hat and gloves from the PPE locker and equip them (place on self). Rhodes will not let you onto the drill floor without them.
3. **Handle pipe.** Carry a drill pipe joint from the pipe rack to the mousehole at the V-door and place it. Carrying a pipe slows the player by 40% unless a second player carries it with them (both hold it). Handoff between players is allowed.
4. **Make up the connection.** At the iron roughneck control stand, run the **timing** skill check: stop the torque needle in the green band. Three attempts; a miss scores lower but does not block.
5. **Check mud pressure.** Read the gauge on mud pump 1 (look at it and press E to log the value), then turn the choke valve handwheel with the **steady-hold** skill check to keep pressure in the green band for 5 s.
6. **Event: kick.** Triggered 10 s after objective 5 completes. A gas influx: alarm siren, red strobes, the flare roars, gauges spike, mud pump 1 trips (station closed). Okafor shouts through the doghouse window. Objectives are replaced: (6a) reach the BOP control panel and press E to lift the guard, (6b) **press-hold** the annular close button for 2 s, (6c) at the choke manifold, **steady-hold** a harder band for 6 s to bleed off pressure through pump 2's line. NPC goals change with the event (Dez runs to the manifold, Mia climbs down, Rhodes heads to the doghouse).
7. **Judgment call.** Rhodes: "We are six hours behind. Skip the flow check and start tripping pipe?" Choice: do the 30-minute flow check (safe) or skip it. Both end the shift, and the choice is graded in the review.
8. **Shift review.** Time, skill-check accuracy, safety rating (PPE, kick response time, judgment choice), team actions in multiplayer, then a career panel: the job ladder (roustabout, floorhand, derrickhand, driller, toolpusher), typical rotation (two weeks on and two weeks off, 12-hour tours), and what workers report loving and hating. Buttons: Play again, Back to lobby.

The shift clock runs at 120x (6 real minutes is a 12-hour tour) and is shown in the HUD.

### Validation: Outer Loop (default) - validate once, not per task

`/build` runs in two phases: **build every task, then validate the whole plan once.** Validation is NOT per-task by default - that's what keeps a build fast.

1. **Build all** - deploy a builder per task in dependency order (independent tasks concurrently). Record each `builder_agent_id`; set the task `state: "built"`. Builders don't touch git.
2. **Outer Validation Loop** - after all tasks are built, deploy the `validator` ONCE over the plan's `## Objective` + `## Acceptance Criteria`. It decomposes them into atomic claims and proves each against the assembled system via oracles (FULL test suite once + queries/greps), catching integration/cross-task failures. Then:
   - `verified` → done.
   - `failed` → dispatch fresh builder(s) scoped to the failing claims (the validator's `### Corrective feedback` says what/where; ledger agentIds say who built that area; no subagent `resume`, so put context in the prompt) → re-validate. ≤3 rounds, then escalate.
   - `unsure` on oracle-less criteria (all-prose) → lighter spec check, accept.

This is the plan's **Final Spec Gate** task - it IS the validation, and it loops.

**Optional per-task review (opt-in, for a risky task only).** A task may declare a `Review` tier to be caught early instead of waiting for the outer gate: `light` = dispatch the `validator` on that task; `full` = `validator` + `code-quality-reviewer` concurrently (`run_in_background: true`, each passed the task ID + `agentId`). On `failed`/`changes-requested`, re-dispatch a fresh builder with the feedback (≤3 rounds). Use sparingly - most tasks declare nothing and rely on the outer gate. The `code-quality-reviewer` only ever runs via this opt-in (or one optional end-of-build pass); it is not a default gate.

### Pipeline Determinism Map

Determinism does not live in the reviewer - an LLM reviewer is non-deterministic. It lives in the **read-only tool outputs and domain scripts the validator cites as evidence.** The validator's job is to push every claim down onto a deterministic oracle; where none exists, it grades `unsure` and names the gap.

| Node | Determinism | Inputs | Output | Notes |
|------|------------|--------|--------|-------|
| Context7 lookup | NON-DETERMINISTIC | API/library names | Current docs/patterns | External state varies |
| Plan creation | NON-DETERMINISTIC | Prompt + codebase + Context7 findings + judgment | Plan document | Inherently judgment-based |
| Builder | NON-DETERMINISTIC | Task spec + atomic acceptance claims | Code changes | Gated by review below |
| Validator (atomic claims) | NON-DETERMINISTIC reasoning over DETERMINISTIC evidence | Acceptance claims + builder transcript (action log) + tool outputs | `STATUS` + `CONFIDENCE` + corrective feedback | Evidence (oracle tool output / domain script) is the deterministic part; the action log scopes navigation; the verdict is graded, not binary |
| Domain scripts | DETERMINISTIC | Code/data state | Pass/Fail oracle | `.claude/agents/team/scripts/*` - accumulated from validator `unsure` gaps |
| Code quality reviewer | NON-DETERMINISTIC | Verified code + diff | approved / changes-requested | Runs only after correctness verified |
| Final Spec Gate | NON-DETERMINISTIC reasoning over DETERMINISTIC evidence | Plan Objective + Acceptance Criteria + finished system | `STATUS` + `CONFIDENCE` | Whole-plan acceptance + integration, spec-only |
